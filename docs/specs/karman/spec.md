## Задача пользователя

Простой личный заметочник по духу Google Keep / Evernote: написать текст, нарисовать, собрать схему или таблицу. Пользователь свободно размещает содержимое на холсте, возвращается к нему с разных устройств и работает без интернета.

## Этапы и объём первой версии — Q33–Q35

Решения пользователя:

- Оффлайн откладывается до следующих этапов (Q33). Первая версия работает при наличии сети.
- Первая версия содержит только основное; остальные согласованные требования переходят в следующие этапы (Q34).
- Детали поведения, не определённые спецификацией, уточняются по мере использования первой версии (Q35).

Требования из разделов ниже сохраняются как согласованные для продукта. Пометка «Следующий этап» означает перенос из первой версии, а не отказ.

### Состав первой версии — Q36

- Вход через Telegram; каждый пользователь видит только свои заметки.
- Список заметок: создание, открытие, переименование, удаление с подтверждением. Сортировка по времени изменения.
- Холст: перемещение и масштабирование, инструменты «Выбор», «Текст», «Перо», «Фигура».
- Текст: перемещаемые блоки с изменяемой шириной, обычный текст.
- Рисование: перо, цвет, толщина, ластик, удаляющий штрих целиком, отмена.
- Схемы: прямоугольники, овалы, привязанные стрелки, текст в фигурах (Q6, Q25).
- Отмена действий в пределах открытия заметки (Q28).
- Автосохранение при наличии сети с состояниями «Сохранено» и «Не удалось сохранить». Неудачное сохранение не выдаётся за успешное; несохранённые изменения остаются в открытой заметке до успешного повтора.
- Поиск по названию и тексту заметок.
- Одновременная работа с двух устройств без потери данных: сохранение проверяет ревизию заметки на сервере. Если заметку уже изменили на другом устройстве, изменения не перезаписывают её молча; пользователь выбирает «Загрузить актуальную версию» или «Сохранить мои изменения отдельной заметкой».

Что заложить сразу, чтобы следующие этапы не требовали переделки данных: устойчивые идентификаторы заметок и элементов, создаваемые на клиенте; версия формата документа; ревизия заметки на сервере.

### Следующие этапы — Q36

- Оффлайн, локальное хранилище и фоновая синхронизация.
- Автоматическое слияние независимых изменений и разбор конфликтов по элементам (Q13–Q15, Q18, Q22–Q23).
- Таблицы.
- Форматирование текста: заголовки, жирный, списки с галочками.
- Папки и закрепление.
- Корзина на 30 дней и восстановление заметки, удалённой на сервере (Q19, Q29).
- Экспорт и импорт `.karman.json`, экспорт PNG.

Таблицы и форматирование текста перенесены в следующие этапы (Q36). Основа холста — Excalidraw (Q37): MIT, бесплатен для опубликованного приложения и уже содержит текст, рисование, фигуры и привязанные стрелки. Для таблиц и форматирования на следующих этапах потребуется собственная доработка поверх Excalidraw.

### Языки разработки и интерфейса — Q38

- Frontend: TypeScript, React, Vite. Excalidraw — React-компонент с типами TypeScript.
- Backend: Telegram Serverless исполняет только JavaScript-модули без npm-пакетов. Исходники писать на TypeScript и компилировать `tsc` в `.js` перед `tgcloud push`; документация платформы такой шаг не описывает, поэтому проверить его в первом прототипе. Запасной вариант — JavaScript с проверкой типов через JSDoc.
- Общие типы формата заметки и API используются и frontend, и backend.
- Имена в коде, комментарии и сообщения коммитов — на английском; документация проекта — на русском.
- Интерфейс поддерживает русский и английский с первой версии. Язык выбирается по `language_code` пользователя Telegram: `ru` — русский, иначе английский. Ручной переключатель — следующий этап.
- Строки интерфейса хранятся в типизированных словарях для двух языков; склонения и даты — через `Intl.PluralRules` и `Intl.DateTimeFormat`. Отдельная библиотека локализации не нужна, пока хватает этих средств.
- Интерфейс Excalidraw переключается его встроенной локализацией (`langCode`), в которой есть русский и английский.
- Пользовательское содержимое заметок не переводится; поиск работает с введённым текстом независимо от языка интерфейса.

### Работа до доступа к Serverless — Q40

- Telegram Serverless для бота пока недоступен: пользователь в листе ожидания.
- Разработка первой версии начинается без Telegram: приложение запускается и проверяется в обычном браузере.
- Интерфейс работает с данными через слой API заметок. До появления backend используется временная реализация с хранением в браузере. Это средство разработки, а не оффлайн-режим продукта.
- Интеграция с Telegram (вход, тема, жесты Mini App), backend на Serverless и проверки в клиентах Telegram выполняются после появления доступа или после отдельного решения пользователя о временном хостинге или другой платформе.
- Срок ожидания доступа не установлен.

## Согласованные требования

### Доступ и устройства — Q2, Q16

- Приложение доступно пользователям Telegram.
- Каждый пользователь видит только свои заметки. Совместного редактирования между пользователями в первой версии нет.
- Вход через Telegram без отдельного логина.
- Целевые клиенты первой версии: Telegram на Android, iPhone и Telegram Desktop на Windows.

### Холст — Q1, Q3–Q4, Q8, Q17

- Заметка — свободный расширяемый холст.
- Текст, рисунки, схемы и таблицы входят в первую версию и могут находиться на одном холсте.
- Элементы размещаются произвольно; пользователь может перемещать их.
- На телефоне холст поддерживает перемещение и масштабирование двумя пальцами.
- Явные инструменты: «Выбор», «Текст», «Перо», «Фигура», «Таблица». Одним пальцем выполняется действие выбранного инструмента, двумя — перемещение и масштабирование холста.

### Текст — Q9

- Текст находится в отдельных редактируемых блоках.
- Блоки можно перемещать и менять по ширине.
- Поддерживаются обычный текст, заголовки, жирное выделение и списки с галочками.

### Рисование — Q5

- Рисование пальцем или стилусом внутри заметки.
- Инструменты: перо, выбор цвета, толщина линии, ластик, отмена действия.

### Схемы — Q6, Q25

- Редактируемые прямоугольники, овалы и соединяющие их стрелки.
- Фигуры содержат текст и могут перемещаться.
- Схема сохраняется редактируемой.
- Стрелки привязаны к фигурам и следуют за ними при перемещении.
- Удаление фигуры удаляет связанные стрелки одним действием; отмена этого действия восстанавливает фигуру и стрелки.

### Таблицы — Q7

- Таблица с текстом в ячейках.
- Добавление и удаление строк и столбцов.
- Формулы и вычисления не входят в согласованный набор первой версии.

### Организация и поиск — Q10, Q20, Q31

Список и поиск входят в первую версию; закрепление, папки и оффлайн-поиск — следующий этап.

- Список заметок.
- Поиск по названию и всему введённому тексту: текстовым блокам, подписям фигур и ячейкам таблиц. Поиск работает оффлайн.
- Закрепление важных заметок.
- Папки без вложенности.
- Удаление папки удаляет и находящиеся в ней заметки. Это уточнение пользователя заменяет ранее предложенное перемещение заметок в «Без папки».
- К заметкам, удалённым вместе с папкой, применяется согласованная корзина на 30 дней. Детали группового восстановления папки и заметок предстоит определить при проектировании.

### Восстановление — Q19, Q28–Q29

Отмена в пределах открытия заметки входит в первую версию; корзина и восстановление удалённой на сервере заметки — следующий этап.

- Удалённые заметки помещаются в корзину на 30 дней и могут быть восстановлены.
- Удаление отдельного элемента на холсте восстанавливается через «Отменить».
- История отмены действует в пределах текущего открытия заметки. При повторном открытии сохраняется результат редактирования, история отмены начинается заново.
- Если после длительного оффлайна заметка уже окончательно удалена на сервере, но на устройстве осталась изменённая версия, пользователь может восстановить её отдельной новой заметкой. Локальные изменения сохраняются до его решения.

### Экспорт и импорт — Q21, Q24, Q26

Следующий этап (Q34).

- Экспорт заметки в редактируемый файл и последующий импорт входят в первую версию.
- Экспорт в PNG для отправки изображения тоже входит в первую версию.
- Редактируемый файл — .karman.json; импорт всегда создаёт новую заметку, даже если исходная уже существует. Исходная заметка сохраняется.
- PNG по умолчанию охватывает всё содержимое заметки с небольшими полями, независимо от текущего положения и масштаба экрана.
- Для большого холста показывается итоговое разрешение; при превышении допустимого размера предлагается уменьшение изображения.
- Конкретная схема переносимого файла, размер полей и ограничения разрешения ещё не определены.

### Сохранение и оффлайн — Q11–Q12, Q30

Оффлайн отложен (Q33). В первую версию входят автосохранение и честные состояния сохранения при наличии сети; остальные пункты раздела — следующий этап.

- Изменения сохраняются автоматически.
- Понятные состояния сохранения: «Сохранено», «Нет связи», «Не удалось сохранить». Точное обозначение локального сохранения и успешной синхронизации ещё предстоит определить.
- После первого входа с интернетом все заметки автоматически загружаются на устройство, включая ранее не открывавшиеся.
- Оффлайн доступны открытие, редактирование и сохранение заметок.
- Локальные изменения отправляются на сервер после восстановления связи.
- Полноценный оффлайн входит в требования первой версии. Подтверждение реализуемости холодного запуска внутри Telegram пока отсутствует.
- При нехватке локального места показывается явная ошибка; уже записанные данные сохраняются, пользователю предлагается экспорт текущей заметки.
- Изменение не отмечается как сохранённое, пока локальная запись не удалась. Возможность экспорта текущего состояния при ошибке записи должна быть предусмотрена отдельно от обычного сохранения.
- Автоматическое удаление заметок ради освобождения места не допускается.

### Синхронизация и конфликты — Q13–Q15, Q18, Q22–Q23

Следующий этап (Q34). В первой версии одновременные изменения обрабатываются проверкой ревизии без автоматического слияния; см. «Состав первой версии».

- Независимые изменения объединяются автоматически. Пример: на одном устройстве изменён текстовый блок, на другом передвинута другая фигура.
- Сравнение учитывает последнюю общую версию, а не только время последнего изменения заметки.
- Пользователь разбирает конфликты по отдельным элементам; остальные изменения заметки сохраняются.
- Для конфликтующего элемента доступны четыре результата: локальная версия, серверная версия, обе версии, свой отредактированный результат.
- «Обе версии» сохраняет две копии конфликтующего элемента на холсте.
- Удаление элемента на одном устройстве и изменение того же элемента на другом считается конфликтом.
- Удаление целой заметки против её изменения тоже считается конфликтом.
- Изменённое содержимое не должно исчезать автоматически при таком конфликте.
- Разные свойства одного элемента объединяются автоматически: например, перемещение текстового блока на одном устройстве и изменение его текста на другом.
- Изменения разных ячеек одной таблицы объединяются автоматически.
- Расходящиеся изменения одного свойства, например текста одной ячейки или положения одной фигуры, показываются как конфликт.
- Границы свойств, структурные изменения таблицы и одновременные действия с рисунком ещё нужно определить.
- Конфликты представлены списком элементов. Для каждого можно переключаться между локальной и серверной версией, видеть изменения и предпросмотр результата.
- Для текста показываются текстовые различия, для рисунков и схем — визуальное сравнение. JSON не является пользовательским интерфейсом разбора конфликтов.
- Разбор можно отложить и продолжать работать с заметкой: обе конфликтующие версии сохраняются, конфликт остаётся отмеченным, независимые изменения продолжают синхронизироваться.
- Перед отправкой решения повторно проверяется текущая серверная версия. Дальнейшее поведение при её изменении ещё предстоит определить.

### Стоимость зависимостей — Q27

- Для первой версии рассматриваются библиотеки, которые можно бесплатно использовать в опубликованном приложении.
- Платные варианты выносятся на отдельное решение пользователя только при существенном преимуществе.

## Исходные технические решения

- Telegram Serverless для backend-функций создания, чтения, изменения и удаления заметок.
- Постоянная SQLite-база платформы.
- Исходно предложена таблица `Notes`: `Id`, `UserId`, `Title`, `Content`, `CreatedAt`, `UpdatedAt`.
- Эта исходная таблица ещё не является финальной схемой. Представление элементов холста, версии, удалений и конфликтов предстоит спроектировать с учётом согласованного оффлайна.
- Согласно документации Serverless, платформа размещает интерфейс, backend и базу; проверенные данные Telegram-пользователя передаются endpoint-функциям платформой.
- Авторизация не заменяет проверку принадлежности заметки пользователю во всех операциях с данными.

## Публикация и обновление — Q39

Правила согласованы пользователем (Q39). Сведения о платформе основаны на документации Telegram Serverless; её канонический адрес и фактическое поведение ещё нужно проверить.

По документации:

- Serverless включается для бота в BotFather; там же выдаётся отдельный токен CLI `tgcloud`. В CI используется переменная `TGCLOUD_TOKEN`.
- `npm run deploy` собирает frontend и выполняет `tgcloud push`, который атомарно выкладывает backend-модули и сборку интерфейса. `push` сам сборку не запускает.
- Интерфейс доступен по адресу `https://app<app_id>.tgcloud.ai/`, endpoint-функции — по `/api/` на том же адресе. Адрес один раз указывается в BotFather как URL Mini App.
- Push проверяет ревизию проекта и отклоняется, если облако изменено с другой машины.
- Изменения схемы базы не применяются при push; их применяет `tgcloud migrate` с подтверждением. Безопасные изменения добавляют таблицы и колонки, удаления подтверждаются отдельно, изменения типа выполняются вручную через SQL.
- Откат выкладки, отдельные окружения, логи продакшена, квоты и цены в документации не описаны.

Правила для Кармана:

- Отдельный тестовый бот со своим `app_id`, базой и адресом используется как staging. Изменения проверяются на нём до выкладки в рабочий бот.
- Откат выполняется повторной выкладкой предыдущего коммита. Миграции базы только добавляющие: старые колонки и таблицы удаляются отдельным шагом после того, как ими перестала пользоваться текущая версия.
- Mini App, открытый до обновления, работает со старым интерфейсом против нового backend. Backend поддерживает предыдущую версию API и формата документа, пока такие клиенты возможны.
- Файлы сборки с хэшем в имени кэшируются как `immutable`, `index.html` не кэшируется долго. Обновление приходит пользователю при следующем открытии Mini App.
- Не добавлять `X-Frame-Options` и ограничивающий `frame-ancestors`: Telegram Web открывает Mini App во фрейме.
- Квоты, лимиты запросов и размера базы, доступ к логам проверить в первом прототипе. Недокументированные ограничения записывать фактическими результатами.

## Внутренний формат: JSON

Пользователь согласовал JSON как основу внутреннего формата. Конкретная схема документа, библиотека редактора и алгоритм синхронизации ещё не выбраны. Ниже перечислены предложения для проектирования, а не реализованная схема.

- Отдельно указывать версию формата документа и ревизию синхронизации. Первая нужна для миграций формата, вторая — для определения изменений относительно общей версии.
- Заметке и элементам холста назначать устойчивые идентификаторы, создаваемые и без сети.
- Хранить элементы по типам: текстовый блок, штрих, фигура, соединитель и таблица. Сохранять координаты, размеры, порядок наложения, стиль и редактируемое содержимое.
- Рисунок сохранять как редактируемые штрихи с точками, цветом и толщиной. Экспорт PNG строится из этого содержимого.
- Текст сохранять структурированно: абзацы, заголовки, выделения, пункты списка и состояние галочек. Конкретная схема зависит от выбранного редактора и пока не определена.
- Табличным строкам и столбцам тоже назначать устойчивые идентификаторы; ячейку определять их парой. Позиция строки в массиве сама по себе не определяет её идентичность при синхронизации.
- Соединители схемы связывать с идентификаторами фигур и их точками привязки. Перемещение и удаление согласованы в Q25; детали выбора точек привязки остаются для проектирования.
- В SQLite `Notes.Content` может хранить JSON содержимого холста; метаданные заметки и данные синхронизации хранятся отдельно от него. Финальное разделение таблиц пока не определено.
- Для синхронизации требуется сохранять общую базовую версию, локальные изменения и сведения об удалениях до их согласования между устройствами. JSON-снимок сам по себе не является протоколом синхронизации.
- Предпочесть готовую библиотеку для структурного diff/patch после проверки на сценариях Кармана. Слияние выполняется относительно трёх состояний: общей исходной версии, локальной и текущей серверной. Применение двух патчей по очереди само по себе не обеспечивает согласованные правила конфликтов.
- Кандидаты для прототипа: `jsondiffpatch` для diff/patch (сопоставление объектов массивов по ID требует `objectHash`; отдельного трёхстороннего merge нет) и `json-merge3` для трёхстороннего слияния (ранняя версия; keyed merge не сохраняет перестановки). Ни одна библиотека пока не выбрана и не установлена. Пользовательские варианты разрешения конфликтов и целостность связей схемы нужно проверить отдельно.
- При проектировании JSON элементы холста сопоставлять по устойчивым идентификаторам. Индексы массивов не должны определять идентичность элемента или ячейки при вставках, удалениях и перестановках.
- По документации Telegram Serverless backend допускает только SDK и собственные модули проекта, без прямого импорта npm-пакетов. Это ограничение нужно учитывать при выборе места выполнения diff/merge и проверке библиотеки; сборка интерфейса имеет отдельные возможности.
- Согласован переносимый файл `.karman.json` и импорт новой копией (Q24). Предлагается включать версию формата, название и редактируемое содержимое; привязку к аккаунту и локальное состояние синхронизации оставлять вне экспорта. Точная схема файла ещё не утверждена.

## Основа холста: кандидаты для проверки

В ответ на предложение пользователя рассмотрены готовые редакторы. Выбран Excalidraw (Q37). До утверждения подробной JSON-схемы оценить его родную модель элементов и избежать дублирования моделей холста. Описание остальных кандидатов сохранено как основание выбора.

- **Excalidraw**: React, холст, рисование, фигуры, привязанные стрелки, JSON и PNG; MIT. В текущих типах элементов текст хранится строкой, отсутствуют полноценные редактируемые таблицы и rich text с галочками. Их добавление может потребовать существенной разработки. Возможности PWA приложения excalidraw.com не следует приписывать встраиваемому npm-редактору.
- **tldraw**: React, расширяемые фигуры, rich text, JSON snapshots, локальное сохранение через IndexedDB; есть пример таблицы как custom shape. Таблицы Кармана и списки с галочками требуют проверки и доработки. По актуальной лицензии production требует действующий ключ trial/commercial/hobby; hobby выдаётся по усмотрению правообладателя и требует watermark. По Q27 нужен бесплатный вариант для опубликованного приложения. Возможность получить подходящую hobby-лицензию не подтверждена; коммерческая лицензия требует отдельного решения пользователя.
- **BlockSuite**: готовые редакторы документов и свободного холста с rich text, JSON snapshots; MPL-2.0. Собственная модель состояния основана на Yjs/CRDT. Соответствие таблиц нашим сценариям, удобство мобильного интерфейса и совместимость с выбранными правилами ручного разрешения конфликтов ещё нужно проверить.

Наличие локального хранилища или multiplayer у редактора не подтверждает холодный оффлайн-запуск в Telegram либо согласованный протокол синхронизации Кармана. Реализация приложения не начата.

## Критерии приёмки для согласования

Границы проверок согласованы в Q32: сквозные сценарии создания смешанной заметки, оффлайна, перезапуска, изменений на двух устройствах, синхронизации, конфликтов и экспорта/импорта проверяются отдельно в Telegram на Android, iPhone и Windows. Правила слияния и доступ только к своим данным дополнительно проверяются автоматически.

Конкретные сценарии ниже подготовлены для итогового согласования; они ещё не выполнены.

### Первая версия

- Сценарий 11 для перечисленных сценариев.

Остальные сценарии относятся к следующим этапам.

### Все сценарии

1. Пользователь создаёт заметку с текстом, рисунком, схемой и таблицей, закрывает её и получает то же редактируемое содержимое при следующем открытии.
2. Пользователь перемещает элементы и масштабирует холст на телефоне; расположение сохраняется.
3. После первой полной синхронизации пользователь открывает ранее не открывавшуюся заметку оффлайн, редактирует её, перезапускает приложение и видит локальные изменения.
4. Пользователь создаёт и сохраняет новую заметку без сети. После восстановления связи она доступна на другом устройстве.
5. Независимые изменения на двух устройствах сохраняются в общей заметке без ручного выбора.
6. Для конфликта одного элемента каждый из четырёх вариантов разрешения даёт выбранный результат; остальные элементы сохраняются.
7. Удаление против изменения элемента или заметки требует решения пользователя и не приводит к автоматической потере изменённого содержимого.
8. Неудачная синхронизация не выдаётся за успешную; локальные изменения остаются доступны.
9. Пользователь находит заметку по названию и тексту, закрепляет её и помещает в папку.
10. Другой пользователь не может прочитать, изменить или удалить чужую заметку.
11. Ключевые сценарии проверены отдельно в Telegram на Android, iPhone и Windows; ограничения каждого клиента описаны фактическими результатами.
12. Перемещение блока на одном устройстве и изменение его текста на другом объединяются; изменения разных ячеек одной таблицы тоже объединяются. Расходящиеся изменения одного свойства требуют выбора.
13. Пользователь восстанавливает заметку из корзины в пределах 30 дней и отменяет удаление элемента на холсте.
14. Пользователь находит заметку оффлайн по тексту из фигуры и ячейки таблицы.
15. Редактируемый экспорт и импорт сохраняют содержимое; импорт создаёт отдельную заметку и не изменяет исходную.
16. PNG охватывает всё содержимое холста с полями, независимо от текущего вида; для слишком большого изображения пользователь видит разрешение и возможность уменьшения.
17. При перемещении фигуры привязанные стрелки следуют за ней; удаление и отмена восстанавливают согласованное состояние фигуры и стрелок.
18. Пользователь видит версии конфликтующего элемента и предпросмотр результата, откладывает разбор и продолжает работать; конфликтующие версии сохраняются, независимые изменения синхронизируются.
19. После повторного открытия заметки последнее сохранённое содержимое доступно, история отмены начинается заново.
20. Изменённая локальная версия заметки, окончательно удалённой на сервере, сохраняется до выбора пользователя; восстановление создаёт новую заметку.
21. При нехватке локального места приложение сообщает об ошибке, сохраняет ранее записанные данные и предлагает экспорт; неудавшаяся запись не отображается как сохранённая, заметки автоматически не удаляются.
22. Удаление папки удаляет находящиеся в ней заметки с применением 30-дневной корзины.
23. Если заметку изменили на другом устройстве после открытия, сохранение не перезаписывает её молча; пользователь загружает актуальную версию или сохраняет свои изменения отдельной заметкой.

Инструменты тестирования пока не выбраны; существующего кода и тестов в проекте нет.
