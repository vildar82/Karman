# Карман

Личный заметочник со свободным холстом в Telegram Mini Apps.

## Требования и этап работы

Перед изменением поведения, архитектуры или плана работ прочитай [спецификацию](docs/specs/karman/spec.md). В ней находятся согласованные требования, открытые вопросы и критерии проверки.

Спецификация согласована. Изменение согласованных требований обсуждай с пользователем и записывай в спецификацию. Реализация идёт по опубликованным задачам.

## Рабочий процесс

- Следуй маршруту: настройка навыков → grilling → согласованная спецификация → задачи → реализация с проверками и ревью.
- Источник выбранного пользователем процесса: `C:/dev/temp/skills`. Навыки читай по точным путям из текущего каталога доступных навыков; при отсутствии регистрации проверяй конкретный файл в указанном источнике.
- Требования храни в `docs/specs/<feature>/spec.md`. Текущая спецификация продукта — `docs/specs/karman/spec.md`.
- Задачи планируются в GitHub Issues этого репозитория. Репозиторий публичный: всё, что попадает в issues, видно всем.
- В ходе обсуждения обновляй спецификацию принятыми решениями; предложения и нерешённые вопросы обозначай явно.

## Git и выполнение задач

Этот порядок применяется при реализации задач и имеет приоритет над Git-шагами навыков, включая указание `implement` коммитить в текущую ветку. Поручение реализовать issue включает коммиты, push ветки и создание PR без повторного запроса разрешения, если пользователь явно не ограничил работу локальными изменениями.

1. **Прочитай задачу в GitHub.** Через `gh` получи актуальные описание, комментарии, критерии приёмки, исполнителя и зависимости. Бери в работу задачу без открытых блокирующих зависимостей. Если issue ещё нет, оформи его по согласованному поручению до реализации.
2. **Создай ветку до изменения файлов.** Проверь рабочее дерево, выполни `git fetch origin` и создай ветку от актуального `origin/main`: `<type>/<issue>-<short-name>`, например `feat/2-app-scaffold`. Для продолжения задачи переключись в её существующую ветку. Сохраняй чужие незакоммиченные изменения; если они мешают переключению, сообщи пользователю. В `main` изменения поступают через PR.
3. **Возьми issue на себя.** Назначь текущего пользователя GitHub исполнителем через `gh issue edit <number> --add-assignee '@me'`. Если уже назначен другой исполнитель, уточни передачу задачи.
4. **Реализуй критерии приёмки.** Используй спецификацию и профильные навыки. Существенные неясности и изменения требований обсуждай с пользователем до зависимой реализации; независимую работу продолжай. Принятые уточнения фиксируй в спецификации и issue; публичные записи не должны содержать приватные данные.
5. **Проверь и отревьюй изменения.** Выполни подходящие проверки из `package.json`, для изменения приложения — `npm run check`. Проверь весь diff задачи относительно `origin/main`, выполни `git diff --check`, проведи ревью по стандартам проекта и требованиям issue. Исправь подтверждённые замечания до отправки на итоговое ревью.
6. **Сделай коммит и push ветки.** Сообщения коммитов — на английском, со ссылкой на issue. Отправь ветку в `origin` с upstream; сохраняй историю опубликованных коммитов, force push — только по отдельному поручению.
7. **Создай или обнови PR в `main`.** Один issue — одна ветка и один PR. Заголовок и описание PR — на русском; укажи результат, проверки, ограничения и `Closes #<number>`. Многострочное описание передавай через `gh pr create/edit --body-file`. Если работа ещё не завершена, используй draft PR и перечисли оставшееся.
8. **Дождись CI и передай результат.** Проверь GitHub Actions для последнего коммита PR. Исправь относящиеся к задаче ошибки и дождись повторных проверок. В итоге дай ссылку на PR, результаты проверок и оставшиеся ограничения; недоступный или упавший CI обозначай явно. Issue реализации остаётся открытым до слияния PR. Слияние выполняй по отдельному поручению пользователя.

## Границы технических решений

В качестве основы выбран Telegram Serverless. Доступ к нему пока не получен (лист ожидания), поэтому первая версия разрабатывается в браузере с временным хранилищем за слоем API заметок. Проверяй доступность платформы и её SDK до реализации интеграции. Изменение платформы согласуй с пользователем.

Продукт выпускается этапами; состав первой версии описан в спецификации. Полный оффлайн, включая повторное открытие, — требование следующего этапа, не первой версии. Данные первой версии проектируй так, чтобы оффлайн и синхронизацию можно было добавить без переделки формата. Перед реализацией оффлайна нужен прототип на Android, iPhone и Telegram Desktop для Windows. Результаты обычного браузера не доказывают поведение Telegram.

Основа холста — Excalidraw на React. Код на TypeScript: имена, комментарии и коммиты на английском, документация на русском. Интерфейс на русском и английском; детали — в спецификации. Механизм локального хранения и протокол синхронизации пока не выбраны.
